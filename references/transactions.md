# Transactions

- `MessageBuilder` implements `MessageBuilding` for one or more local V1 SOL transfers sharing one sender. The same encoder supports a payment followed by service tips. `Transfer` supplies validated `Address` values and positive `UInt64` lamports; the sender pays fees.
- `MessageBuilder` also implements `TokenMessageBuilding` for SPL Token and Token-2022 through one `TokenTransfer` API. Both share the V1 encoder with SOL; all construction remains local and single-signer.
- Decode `TokenMint` and `TokenAccount` from raw RPC bytes and program owners. Transfers validate the source authority, mint/program relationships, balances, recipient ATA, frozen state, and required extensions. RPC observations must share a network and consistent ledger context; they do not prove provider honesty or freshness.
- Recipient ATA derivation includes the token program. An absent destination adds idempotent ATA creation, funded by the sender; rent is separate from the token amount and transaction fee. Public-address derivation uses SHA-256 and a bounded Ed25519 curve-membership check, separate from signing.
- Token-2022 fees use integer ceiling division, the observed epoch, and the configured cap. `TransferCheckedWithFee` asserts the expected fee on-chain. Required incoming memos precede the transfer. Amounts always use raw units, including interest-bearing and scaled-UI mints.
- Transfer hooks needing extra accounts, confidential-transfer extensions, and unimplemented extensions return `TokenError.unsupportedExtension`; they are never silently ignored. Nontransferable/paused mints and frozen accounts fail explicitly. Token workflow integration and UI remain later work.
- Supply a recent blockhash and explicit `Configuration`: total priority-fee lamports, compute units, and loaded-account bytes. Optional heap size defaults to the protocol's 32 KiB. Limits are validated, never silently clamped; simulation must establish sufficiency.
- `message(for:recentBlockhash:configuration:)` returns unsigned `Data` for fee estimation and signing. `Wallet` supplies the signature; `TransactionBuilder: TransactionBuilding` verifies it against the message's sole signer and appends the V1 signature field. `simulationTransaction(for:)` instead appends an empty signature slot for unsigned simulation only. The internal app [transaction coordinator](transfers.md) owns review and signing workflows; see [architecture](architecture.md).
- For supplied envelopes, `TransactionBuilder.validateSignatures(in:for:)` verifies all occupied slots and requires an empty slot for the selected signer. `transaction(byAdding:for:to:)` returns a typed `Transaction` after verifying the new signature and filling only that slot, preserving the message and all cosigner slots. Other signatures may remain missing. The general `validateSignatures(in:)` overload supports verification before submission. Both assembly paths share strict Ed25519 verification.
- The shared [Encoding](encoding.md) codec supplies strict Base58; Transactions requests exactly 32 bytes for addresses and blockhashes. Self-transfers reuse the signer index. The invoked System Program cannot be a transfer account.
- `TransactionDecoder: TransactionDecoding` imports binary or bounded Base64 V1 envelopes up to 4,096 bytes into typed values. `Transaction` preserves exact message bytes, account roles, optional resource requests, opaque instructions, and ordered signature slots. Unknown versions/configuration bits, malformed lengths, duplicate accounts, and invalid indices are rejected. `serializedRepresentation` preserves the original message and signature slots; `signature` exposes the first populated slot as Base58. Omitted and zero-valued requests remain distinct; inspection doesn't verify signatures, interpret program intent, or establish runtime acceptance.
- Construction is synchronous, bounded, and stateless; values are `Sendable`. Transactions handles no recovery material, private keys, networking, or UI. Single-signer construction checks the header and size; supplied envelopes also pass full structural decoding. Neither path interprets instruction payloads. Encoding and signature verification don't establish intent, account existence, funds, blockhash freshness, or live V1 availability.
- Signature verification rejects all fourteen small-order Ed25519 encodings in the signer and signature point before using CryptoKit. This check belongs to signing, not recipient-address validation. Regression fixtures cover identity-key forgery and a strong key with an identity nonce point; the latter is generated offline as `S = SHA512(R || A || message) × a mod L` with `R` equal to the identity.
- Focused Swift Testing tests cover independent wire fixtures and meaningful invalid inputs. Message fixtures use the public accounts in Solana's [V1 examples](https://github.com/solana-foundation/transaction-v1-examples/blob/main/ts/kit/test/wire.test.ts), generated offline with `@solana/kit` 8.0.0 and `@solana-program/system` 0.13.0. The signed fixture uses the public BIP-39 zero-entropy phrase at `m/44'/501'/0'/0'`, a one-SOL transfer, a zero blockhash, and explicit resource limits: Node PBKDF2/HMAC derives the key, Kit signs `compileTransaction(message)`, and `getBase64EncodedWireTransaction` encodes it. Neither package is an app or test dependency.
- Decoder tests use an independent Kit fixture with two signers and two instructions, including repeated account references and deliberately unverified signatures. They cover every truncated prefix, the maximum envelope size, sliced `Data`, account bounds, and configuration handling.
- Token verification (2026-09-28): Kit 8.4.0, Token 0.17.0, and Token-2022 0.19.0 provide independent instruction/account fixtures and PDA/curve vectors; no SDK is a runtime dependency. All 43 Transactions, 46 RPC, and 32 app tests pass on iPhone Duo, along with Debug/Release builds. Three read-only Helius devnet requests verified both native mints and missing ATAs at slot `505187600`; token signing/broadcast and extension execution remain unverified live.
- Live devnet verification (2026-09-27): a disposable macOS Swift harness compiled the framework sources, created a memory-only wallet, verified funding and DAS balance, then built, signed, simulated, and submitted a 0.001 SOL transfer through Helius. The [finalized V1 receipt](https://explorer.solana.com/tx/4RwM4AhqaZNpqPaert6YEKYL7EZfKyqhESo9cwyheivg69Kfd4AG2nKH8mRNZtwk1QuJGyoMvBFbsfCWnFUGZ9YB?cluster=devnet) reports no execution error, 150 compute units, a 5,000-lamport fee, and matching final balances. This establishes devnet acceptance, not mainnet activation; the disposable wallet's recovery material was not persisted.
