# Transactions

- `Instruction` contains a program address, ordered account permissions, and opaque data. `SystemProgram.transfer`, `MemoProgram.memo`, and `TokenTransfer.instructions()` produce these same composable values. Program helpers never compile or submit their own transactions.
- `MessageBuilder: MessageBuilding` compiles any ordered instruction collection with an explicit fee payer, blockhash, and `Configuration`. It merges account privileges, preserves repeated instruction arguments, and reserves every required signature. The payer need not be an instruction's authority. One composition stays atomic: exceeding V1's 4,096-byte envelope, 64-account, 64-instruction, or 12-signature limits throws; nothing splits automatically.
- `Configuration` specifies total priority-fee lamports, compute units, loaded-account bytes, and optional heap size. Explicit values are validated without clamping. The app estimates defaults before review; framework construction remains synchronous, bounded, stateless, and `Sendable`.
- `TransactionDecoder: TransactionDecoding` imports binary or bounded Base64 V1 envelopes, preserving exact message bytes, account permissions, resource requests, instructions, and signature slots. It rejects unsupported versions/configuration, malformed lengths, duplicate accounts, and invalid indices. Decoding doesn't verify signatures or interpret program intent.
- `ProgramAddress.find(seeds:program:)` returns a program-derived address and its canonical bump, searching bumps from 255 down; more than 15 seeds or a seed over 32 bytes throws. `Address.bytes` exposes an address's 32 bytes for seeds and instruction data.
- `TransactionBuilder: TransactionBuilding` structurally validates unsigned envelopes and allocates one empty slot per required signer. Signature insertion verifies the existing signatures and the new signature, fills only the selected empty slot, and preserves all other bytes. Imported and locally composed transactions use the same assembly path.
- Strict Ed25519 verification rejects small-order encodings in both the public key and signature point before CryptoKit verification. This restriction belongs to signing; recipients may be program-derived addresses. Addresses and blockhashes use the shared strict ASCII Base58 codec.
- `TokenMint`, `TokenAccount`, and `TokenTransfer` validate SPL Token and Token-2022 observations together: authority, mint/program relationships, balances, destination ownership, frozen state, and supported extensions. Token instructions can be composed with any other program. The token owner funds any ATA creation.
- A recipient address that is a token account for the mint receives the tokens directly, and its owner is the recipient; mints, other token-program accounts, and executable programs are rejected. Any other address is a wallet that receives at its ATA.
- Missing ATAs and empty, nonexecutable System Program-owned ATAs add idempotent creation; initialized token accounts do not. `TokenMint.associatedAccountSize` is 165 bytes for Token, or 170 plus required supported extension storage for Token-2022. The app queries rent separately and subtracts any existing destination lamports from the required deposit, with a minimum of zero; it isn't part of network fees or token amounts.
- Token-2022 transfer fees use integer ceiling division, the observed epoch, and the configured cap; checked instructions assert the fee on-chain. Incoming memos precede the transfer. Raw units remain authoritative for scaled/interest-bearing mints. Unsupported hooks, confidential transfers, and unknown extensions fail explicitly; paused, nontransferable, and frozen state cannot be silently ignored.
- The Kit, Token, and Token-2022 SDKs generate test fixtures only.

See [the app workflow](transaction-workflow.md) for simulation, approval, and submission. Recovery material, networking, and UI stay outside this framework. Durable nonces aren't supported.
