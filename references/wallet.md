# Wallet

- Wallet provides local recovery phrase creation/import and Solana address derivation.
- New phrases default to 12 English BIP-39 words. All five standard lengths are supported.
- `Wallet` implements `WalletProviding`; `RecoveryPhrase` validates imports. The service retains no secrets and makes no network or persistence calls.
- Address derivation uses BIP-39 passphrases and hardened SLIP-0010 Ed25519 paths, defaulting to `m/44'/501'/0'/0'`. Recovery requires the original passphrase and exact account path. `WalletProviding.accounts` derives an ordered batch of public addresses and paths using one temporary BIP-39 seed; Wallet remains local and cryptographic.
- Automatic discovery uses the internal, protocol-based `AccountDiscovery` coordinator. It checks `m/44'/501'/i'/0'` and `m/44'/501'/i'` on the selected RPC network. The initial scan covers indices 0–9 in each family: twenty addresses in one `GetMultipleAccounts` request. Callers may explicitly request another range of at most ten indices; there is no automatic continuation. Results carry their network, scanned range, next range, and each discovered address's exact path.
- Discovery keeps only addresses with a positive SOL balance. By explicit product decision, zero-SOL and missing accounts are ignored even if they own tokens or have transaction history. No token, history, or DAS lookups are performed. RPC receives only public addresses; errors and cancellation fail the scan without retries or a misleading empty result.
- Import preparation scans mainnet and selects the first positive-SOL account in scan order; a successful empty scan selects `m/44'/501'/0'/0'`. Creation remains local, and phrase validity is independent of balances. Each window retains its selected account and recovery IDs across persistence retries without rescanning or repeating committed writes.
- Account metadata stores the exact validated derivation path used for signing. Missing or invalid required fields fail loading without modifying saved records.
- Application Support, which holds account metadata and themes, is excluded from device backups on every launch. No app data syncs or restores to another device.
- An empty scan means no positive SOL balances were found within that range. It cannot prove non-use, validate a BIP-39 passphrase, or discover accounts outside the supported paths/range. Explicit-path derivation remains available for other hardened paths.
- CryptoKit supplies SHA-256, HMAC-SHA512, and Ed25519. Security supplies secure randomness. Standard word-list data is included locally; no third-party runtime dependency.
- The shared [Encoding](encoding.md) framework supplies Base58 address encoding; Wallet doesn't maintain a separate codec.
- Verification uses published vectors and independently derived addresses. Only public test phrases are fixtures.
- `Wallet` also implements `MessageSigning`: `signature(for:using:expectedAddress:passphrase:path:)` signs exact bytes with CryptoKit after strict Base58 validation and a recovered-account check. Address derivation and signing share the same key derivation pipeline. Signing is `@concurrent`, checks cancellation, retains no secret state, and neither authenticates nor interprets transaction intent; the caller owns those steps.
- Verify signatures cryptographically, not by deterministic byte equality: [CryptoKit may randomize signatures](https://developer.apple.com/documentation/cryptokit/curve25519/signing/privatekey/signature(for:).md). Tests use public fixtures, reject mismatched and Unicode-lookalike senders, and verify cancellation. Swift does not guarantee secret memory erasure.
- `Vault` implements secure persistence and authenticated access. The internal app [transaction coordinator](transaction-workflow.md) owns review and signing workflows under [architecture](architecture.md); the Wallet framework stays local and cryptographic. UI remains a later milestone.
- Approved storage access: biometrics or the device passcode, interchangeably. A device passcode is required; biometrics are optional. Biometric enrollment changes don't affect access. Removing the device passcode deletes recovery, which then requires the backup phrase and any original BIP-39 passphrase.
- Approved storage boundary: a separate `Vault` framework exposes `RecoveryStoring`, implemented by `KeychainStore`, for saving, retrieving, and deleting recovery material.
- Storage is device-only: no iCloud synchronization or cloud backup of recovery material. Use non-synchronizing Keychain items with `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` and `userPresence`.
- Onboarding and backup guidance must explain that the recovery phrase is the only recovery method; neither the app nor iCloud can restore it. Losing the device or removing its passcode requires the backup. Any original BIP-39 passphrase and derivation path are also required; device authentication does not replace the backup.
- `KeychainStore(service:)` saves a `Recovery` under a caller-owned UUID, rejects overwrites, retrieves it with `recovery(for:reason:)`, and removes it with `deleteRecovery(for:)`, or every wallet's with `deleteAllRecovery()`. Failed reads preserve storage. Cancellation dismisses authentication but doesn't undo completed writes or deletions.
- Vault is implemented and tested. Coverage includes storage policy, recovery, duplicate protection, failures, cancellation, deletion scope, redaction, and real simulator Keychain behavior with and without biometric enrollment; use the [biometric-tests skill](../.agents/skills/biometric-tests/SKILL.md).
- Specific device-validation caveat: simulator Keychain reads can succeed without an authentication prompt. Physical-device authentication and passcode fallback require device validation; preserve the current storage policy.
