# Project constraints

- Keep this file lean: user-approved restrictions and clarifications only.
- Keep skills machine-independent: discover local devices and paths instead of hardcoding them.
- Use only three simulators for development and verification: one regular iPhone, one iPad, and one iPhone Duo. Reuse existing devices; do not create additional simulators or expand this matrix without explicit user approval.
- Use Conventional Commits format for every commit.
- Commit or explicitly discard each milestone before starting the next; keep completed milestones in separate commits.
- Do not add module-name prefixes to types; rely on the module namespace.
- Keep project files grouped by concern in real folders that Xcode mirrors; organize UI features into focused subfolders for scenes, screens, sections, components, and models as needed. Group related tests accordingly.
- Keep app source and tests in `App/Sources` and `App/Tests`. Keep every framework in `Frameworks/<Module>` with `Sources`, `Tests`, and `README.md`.
- Keep test helpers shared by frameworks in `Frameworks/TestSupport`.
- Give every framework a concise, factual `README.md` for third-party readers; omit project history, progress reports, and agent-only guidance.
- Prioritize simplicity, readability, and ease of extension throughout the app and tests; follow Don't Repeat Yourself and Single Concern.
- Prioritize developer experience: express intent with typed APIs and encapsulate serialization and transport details inside services.
- Use protocol-oriented programming throughout: depend on protocols and inject concrete implementations.
- Compose wallet workflows in internal app services/coordinators, outside views; keep frameworks focused on reusable concerns. Follow [references/architecture.md](references/architecture.md).
- Expose only contracts and values needed across module boundaries; keep implementation helpers internal or private.
- iOS 27.1+ with full iPhone Duo support; no older-iOS compatibility paths.
- Use [SwiftUI Expert](plugin://swiftui-expert@swiftui-expert-skill) for UI work. Follow [UI architecture](references/ui.md) for adaptive `NavigationSplitView` navigation, with the approved onboarding `NavigationStack`/`ArrangementView` exception, theme packs, and HIG requirements for app-owned UI and built-in themes; do not gate user-created packs on HIG aesthetics.
- Prefer SwiftUI. Use UIKit only when required functionality cannot be achieved with SwiftUI or a concrete performance need justifies it.
- **Hard rule:** Never extract UI into view-returning computed properties or helper functions, including `@ViewBuilder` helpers. Every extracted view/component must be an independent `View` type in its own Swift file. Protocol-required rendering entry points and thin modifier/style convenience APIs are exempt; other helpers may return data or perform actions, not compose views.
- When creating custom view modifiers, styles, or similar SwiftUI APIs, provide and use a fluent convenience helper, such as a `View` extension for a modifier or a static member for a style. Keep it with the underlying type and delegate directly to that type without duplicating behavior or branching the view hierarchy.
- Keep interaction feedback visually stable; do not flash progress rows, spinners, or disabled states for quick actions, including preference changes and theme package operations.
- When a screen has a single call to action (CTA), pin it to the bottom in a soft toolbar so it remains visible while content scrolls. Respect safe areas and keep the content unobscured.
- Constrain readable content, not its `Form`, `List`, or `ScrollView` viewport. Preserve scroll indicators at the container's safe-area edge, size pinned actions independently, and verify indicator placement during layout reviews.
- Treat motion as part of the UI: use native animations for meaningful state changes, including row insertion and removal. Add explicit `accessibilityReduceMotion` checks only for pronounced animations identified by the user, not every animation.
- Support simultaneous wallet windows where the system allows them; keep each window's wallet selection, navigation, and presented tasks independent.
- Own appearance loading and resolved palettes at each window's root. Inject the palette and tint there; feature scenes and screens inherit appearance through the environment instead of receiving or loading it separately. Share appearance services across windows, not their rendered state.
- Swift 6 with the latest compiler, SDK APIs, Apple guidance, and supported upcoming language features. No deprecated approaches.
- Pure Swift and Apple frameworks; avoid third-party dependencies where reasonable.
- Use `'/Applications/SF Symbols.app/Contents/Executables/sfsymbols'` when interacting with SF Symbols.
- Validate concurrency changes against current Apple documentation and the Swift Concurrency plugin's `swift-concurrency` skill.
- Follow [references/testing.md](references/testing.md) when writing or reviewing tests.
- Verify RPC integrations with real clients on devnet; do not add fake RPC implementations for tests.
- Never request funding for a wallet without verified, retained recovery. Reuse controlled devnet test wallets and return test funds after fees; never discard funded wallet recovery.
- Document every function and initializer using Apple DocC conventions.
- Solana V1 transactions only; compose ordered instructions through one shared transaction pipeline. Transfers are instruction helpers, not a separate transaction model.
- Support SPL Token and Token-2022 together through shared token-transfer APIs. Review and agree on each Token-2022 extension with the user before implementing it.
- Separate frameworks by concern; all Solana RPC, DAS, and price-provider communication belongs in the RPC/API framework.
- Keep RPC, DAS, and pricing contracts provider-neutral. Helius and Jupiter are implementations; providers must be interchangeable behind protocols and transform responses into shared types.
- Surface rate-limit errors to consumers; do not automatically retry. Pace price-provider batches within their request budgets; do not throttle Solana RPC or DAS requests.
- Add RPC methods only for concrete needs of agreed wallet features; follow [references/rpc-scope.md](references/rpc-scope.md), not endpoint coverage.
- Keep the app decentralized: no app-owned backend or proxy. Connect directly to Solana RPC providers.
- Use one submission strategy: `none` sends identical signed bytes concurrently through configured same-network ordinary RPCs; `standard` and `premium` use Sender exclusively. Follow [references/transaction-workflow.md](references/transaction-workflow.md).
- Use the selected provider's DAS interface only for portfolio viewing; keep DAS out of transaction submission contracts, validation, and routing. Follow [references/portfolio.md](references/portfolio.md).
- Keep wallet recovery material device-only, excluded from iCloud sync and backups; follow [references/wallet.md](references/wallet.md).
- Discover accounts with one SOL-only lookup for twenty addresses; intentionally ignore zero-SOL accounts. Follow [references/wallet.md](references/wallet.md).
- Agree on architecture before implementation; work on one concern at a time.
- Resolve unapproved UI design and behavior with the user before implementing it; do not infer production approval from disposable mockups. Follow [references/ui.md](references/ui.md).
- Complete the agreed framework milestones before App/UI work; handle Portfolio last. Follow the current sequence in [references/architecture.md](references/architecture.md).
- Request documentation as Markdown by appending `.md`. Apple API docs: `https://developer.apple.com/documentation/<path>.md`; tutorials/design guidance: `https://developer.apple.com/tutorials/data/<path>.md`.

Keep [references/](references/) concise: current approved decisions, behavior, and limitations only. Do not add project history, dated progress reports, or test-run results; keep unapproved designs out.
